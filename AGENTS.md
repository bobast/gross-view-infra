# AGENTS.md

## Project Overview

This repository manages **infrastructure configuration** for the "gross-view" project. It contains Keycloak realm settings, Nginx reverse proxy configuration, and custom CSS styles for authentication forms.

> **Requirement:** any change to the repo (files, services, network, code, config) — from an agent or a human — **must** be reflected back into this file (structure, notes, IP map, new services, new conventions). After every modification, review AGENTS.md and update it if the change makes current instructions inaccurate or incomplete.

## Repository Structure

- `nginx/gross-view.local.conf` — Nginx site config for `gross-view.local` (docker-compose; in K8s mirrored by `k8s/base/nginx-configmap.yaml` for production `mint-box.ru`)

- `docs/opencode-mcp-integration.md` — Как MCP-сервер gross-view-handler (`/api/mcp`) подключается к агенту opencode; docker-реализация и K8s-план, JWT/workspace-архитектура, токены
- `handler/entrypoint.sh` — Точка входа контейнера `handler` для контейнеризованного/K8s варианта (импорт self-signed `certs/gross-view.local.crt` в JVM-cacerts, Nimbus JWKS через `https://gross-view.local/sso/...`). **В docker-compose сервис handler отсутствует** — локально handler запускается в режиме отладки на хосте (см. ниже)
- `opencode/entrypoint.sh` — Точка входа контейнера `opencode` (docker): рендер `/root/.config/opencode/opencode.json` с remote MCP `gross-view`, а также генерация primary-агента `mcp-first` и справочного skill `mcp-first`. **Авто-генерация токена**: если `OPENCODE_MCP_TOKEN` пуст, получает `client_credentials`-токен из Keycloak через `KEYCLOAK_INTERNAL_URL` + `OPENCODE_AGENT_CLIENT_ID`/`OPENCODE_AGENT_CLIENT_SECRET`. **Re-entry логика**: при старте токен переиспользуется из существующего `opencode.json`, а JWT-claim `exp` проверяется декодированием base64url payload (без jq) — если токен протух или недоступен, entrypoint обновляет его из Keycloak/`.env` (не полагаясь на ручной `restart`). **Устойчивость**: попытки повторяются до `OPENCODE_TOKEN_MAX_ATTEMPTS` (default 10, пауза 2 s), причина отказа всегда логируется (`Response: …` — busybox wget печатает её даже с `-q`), и **рабочий `opencode.json` никогда не удаляется** при сбое — старый конфиг сохраняется с предупреждением (иначе transient-сбой Keycloak молча оставлял opencode без MCP, а UI показывал «серверы не обнаружены» без причины). В `docker-compose.yml` аналогичная защита от race-условия на старте: `keycloak` имеет `healthcheck` (TCP-probe на порт 8080 через `/dev/tcp` — в образе нет curl/wget/busybox, но есть bash+timeout), а `opencode` стартует только через `depends_on: keycloak: condition: service_healthy`. Образ opencode — BusyBox, **`curl` в нём отсутствует**, поэтому используется `/usr/bin/wget` (нет TLS-стека → только внутренний plain-HTTP Keycloak). K8s-версия скрипта — `k8s/base/opencode-entrypoint-configmap.yaml` (обязана быть идентичной docker-версии; для неё в `.gitattributes` добавлен `text eol=lf`, чтобы CRLF-конвертация не ломала встроенный скрипт)

## Purpose

This repo manages reverse proxy routing, Keycloak theme customizations, realm settings, and multi-container orchestration. Nginx provides unified entry point routing `/sso` to Keycloak, `/api` to the **handler backend (gross-view-handler)**, and `/` to frontend. The handler runs its own **MCP-сервер** (`/api/mcp`), к которому обязателен подключён ИИ-агент opencode (см. `docs/opencode-mcp-integration.md`).

## Infrastructure Services

### Static network

- Static network: every service has a fixed IP. In docker-compose nginx (80/443), keycloak (8080), and **opencode (4096)** publish host ports; **postgres exposes no host port** (reachable only inside `keycloak_network` at `172.28.0.2`). **handler (gross-view-backend, порт 8082) в compose отсутствует** — он запускается в режиме отладки на хостовом компьютере, а nginx/opencode обращаются к нему через `host.docker.internal:8082`. In K8s opencode stays internal (ClusterIP, no LoadBalancer/hostPort).
- `172.20.x`, `172.19.x`, `172.18.x` are taken by the host/WSL and other Docker networks — avoid them.

## Important Notes

- Nginx config changes affect routing for the entire `gross-view.local` site. In K8s the routing lives in `k8s/base/nginx-configmap.yaml` (production domain `mint-box.ru`); `k8s/base/ingress.yaml` (ingress-nginx) is kept for reference only and is excluded from the kustomize build — keep the nginx config and ingress in sync if either is changed. Changes to the nginx ConfigMap require a Deployment rollout: `kubectl -n gross-view rollout restart deployment/nginx`.
- CSS changes affect the visual appearance of Keycloak login/registration screens
- Realm JSON should only be modified carefully — it defines clients, roles, mappers, and identity providers
- Do not add application source code here — this is configuration-only
- When editing `login.css`, ensure compatibility with Keycloak's FreeMarker templates (IDs/classes used in forms may vary by Keycloak version)
- `login.css` supports light/dark via the `data-theme` attribute on `<html>`; keep the semantic tokens (`--color-surface`, `--color-body-bg`, `--color-on-accent`, `--color-accent`, status tokens) in `:root` and the `[data-theme='dark']` block in sync with `src/app/index.css` of gross-view-ui
- The theme is applied to the login page by `js/theme.js` (declared via `scripts=` in `theme.properties`); its storage key must match `THEME_STORAGE_KEY` in `src/features/theme/model.ts` of gross-view-ui
- Keycloak locale support is declared in two places, keep them in sync: the realm's `supportedLocales` (`gross-view-realm.json`) and the theme's `locales` in `themes/gross-view/login/theme.properties` (currently `en,ru,zh-CN`; message bundles `messages.properties`, `messages_en/ru/zh_CN.properties`). **Bundle naming is critical (diagnosed 2026-09-14):** Keycloak 23 renders login/register messages only from the bundle `messages` — files must be named `messages_<locale>.properties` in `themes/gross-view/login/messages/`. The old `login_*.properties` convention (bundle `login`) was silently ignored (verified live: the ru page rendered stock `E-mail`/`Войдите в {0}` instead of the custom strings, and `zh` fell back to English). Chinese must use the Keycloak-native tag **`zh-CN`** (stock bundle is `messages_zh_CN.properties`, dropdown label `locale_zh-CN=简体中文`); a bare `zh` resolves no translation file and renders English. gross-view-ui must write the cookie/`ui_locales` as `zh-CN` too (theme.js maps both `zh`/`zh-CN` to display but always emits `zh-CN`). The realm import runs only against a fresh DB — editing `gross-view-realm.json` does NOT update an already-imported realm, so toggle `Supported locales` in the admin console (Realm Settings → General) for running environments (или через `kcadm.sh update realms/gross-view-realm -f <json>`; локальный dev-realm уже обновлён до `en,ru,zh-CN` 2026-09-14). The theme files (docker-compose `./themes:` volume / K8s ConfigMap) are picked up on a Keycloak restart.
- Keycloak hostname: `kc-hostname` or `KC_HOSTNAME_URL`/`KC_HOSTNAME_ADMIN_URL` in `k8s/base/keycloak-deployment.yaml` point at `https://mint-box.ru/sso` (production). docker-compose (local dev) keeps `gross-view.local` values. The realm's redirectUris contain both `gross-view.local` and `mint-box.ru` — keep these in sync when changing domains.
- Do not commit or log: `OPENCODE_AGENT_CLIENT_SECRET`, `OPENCODE_MCP_TOKEN`, or contents of `.env` / `certs/`
- **Line endings:** `.gitattributes` pins `*.sh` to `text eol=lf` and `*.ps1` to `text eol=crlf` (overrides the local `core.autocrlf=true`). Never let shell scripts keep CRLF — a BusyBox ash container breaks with `/entrypoint.sh: set: line 2: illegal option -` (the `\r` becomes part of the `set` option). Create/edit scripts with LF only and keep `opencode/entrypoint.sh` ↔ `k8s/base/opencode-entrypoint-configmap.yaml` (embedded `data.entrypoint.sh`) identical; both were regenerated to LF + clean UTF-8 in the 2026-09-09 fix.
- MCP ↔ opencode (docker): **handler в docker-compose отсутствует** — backend `gross-view-handler` (Spring Boot, порт 8082) запускается локально в режиме отладки на хостовом компьютере, а nginx проксирует `/api` → `http://host.docker.internal:8082` (в opencode для этого прописан `extra_hosts: host.docker.internal:host-gateway`). Handler требует `CREDENTIAL_ENCRYPTION_KEY` (AES-GCM 32 байта, base64; fail-fast) и публикует нацию (`opencode`, Basic → `OPENCODE_SERVER_PASSWORD` с fallback на старый `OPENCODE_PASSWORD`). Агент `opencode` регистрирует remote MCP `gross-view` на `http://host.docker.internal:8082/api/mcp` (переопределяется через `OPENCODE_MCP_URL`) с Bearer-токеном service-account клиента `opencode-agent` (роль `MCP`, `access.token.lifespan=86400`). Токен **авто-генерируется** entrypoint-ом на старте из `KEYCLOAK_INTERNAL_URL` + `OPENCODE_AGENT_CLIENT_ID`/`OPENCODE_AGENT_CLIENT_SECRET` (busybox wget, нет curl; ретраи до `OPENCODE_TOKEN_MAX_ATTEMPTS`, при сбое рабочий `opencode.json` сохраняется — см. `opencode/entrypoint.sh`); ручной переопредел — `OPENCODE_MCP_TOKEN` (`scripts/get-opencode-mcp-token.ps1`). Без токена MCP-сервер не регистрируется. Service-account должен быть членом workspace (роль `ANALYST` достаточна для финансовых MCP-инструментов; bind происходит к **первому** членству при `initialize`). Для контейнеризованного варианта `handler/entrypoint.sh` импортирует self-signed `gross-view.local.crt` в JVM-cacerts (`changeit`), поэтому для JWKS обязателен `extra_hosts: gross-view.local:172.28.0.4`. В realm добавлены роли `MCP`/`ANALYST`/`ADMIN` и конфиденциальный клиент `opencode-agent` (secret placeholder `changeme-opencode-agent` — сменить при накате). Детали/вопросы v1 vs v2 токенов — в `docs/opencode-mcp-integration.md`.
- **MCP-first агент**: entrypoint генерирует primary-агента `mcp-first` (`mode: primary`, `permission: edit/write: deny`) с промптом, обязывающим проверять MCP-инструменты gross-view первыми. `opencode.json` содержит `"default_agent": "mcp-first"` — стоковый `build` доступен через `opencode run --agent build`. Source-файлы агента и skill живут в репозитории (`.opencode/agent/mcp-first.md`, `.opencode/skills/mcp-first/SKILL.md`) и копируются entrypoint'ом в `/root/.config/opencode/` при старте.
- **Диагностика LLM-ошибок в UI** (gross-view-handler + gross-view-ui, 2026-09-10): провал вызова модели (сервер OpenCode пишет `info.error`, напр. `APIError`/`Insufficient Balance`, `statusCode: 402`) теперь не выглядит как «пустой контекст»: handler пробрасывает `error` из `OpenCodeMessageInfo` и из ответа `/opencode/chat|/analyze` (`LlmAnalysisResult.error`), а UI рисует красный баннер «Ошибка модели» в пузыре ассистента. Попутно исправлена десериализация форматов сервера: токены принимают вложенный `cache:{read,write}` (плоский `cache_read/write` — контракт с UI при сериализации), временные метки сообщений — `created/completed` (плюс `start/end`), в `info` добавлены `modelID`/`providerID`, и `/chat` возвращает реальную модель `providerID/modelID` вместо `role`. Если после этого в UI снова «Токены: 0» без баннера — причина в другом (проверить баланс DeepSeek: `https://platform.deepseek.com`).

## Kubernetes (K8s) deployment

The `k8s/` directory mirrors the docker-compose stack for cloud/K8s. Both describe the same services; keep them in sync.

- Apply with `kubectl apply -k .` from the repo root. The **root** `kustomization.yaml` uses `configMapGenerator` to embed the Keycloak theme (`themes/gross-view/`) and realm (`gross-view-realm.json`) into ConfigMaps because kustomize cannot reference files outside its own directory.
- Service → manifest mapping (all in `gross-view` namespace):
  - postgres → `k8s/base/postgres-statefulset.yaml` (StatefulSet + headless `Service` + `volumeClaimTemplates`, `postgres-init` ConfigMap for init scripts)
  - keycloak → `k8s/base/keycloak-deployment.yaml` (Deployment + `Service`, mounts generated `keycloak-theme` / `keycloak-realm` ConfigMaps). Health/probes hit Keycloak **directly on container port 8080** (no `/sso` prefix — that path exists only behind nginx): `startupProbe` on `/health/started` (must be long enough for the Quarkus build that `start --import-realm` runs on a cold 23.0.6 image — killing early causes CrashLoopBackOff / `connection refused` on 8080), `readinessProbe` on `/health/ready`, `livenessProbe` on `/health/live`. The theme ConfigMap is flat (keys without `/`); each theme file is mounted with `subPath` to its nested path under `/opt/keycloak/themes/gross-view/login/...` (ConfigMap data keys cannot contain `/`; the `gross-view/` theme-name directory level is required for Keycloak to resolve the theme — missing it silently falls back to the stock `keycloak` theme). Keep the root `kustomization.yaml` configMapGenerator file keys (`theme.properties`, `messages.properties`, `messages_en.properties`, `messages_ru.properties`, `messages_zh_CN.properties`, `login.css`, `theme.js`) and the keycloak-deployment subPath mounts in sync when adding theme files.
  - nginx → `k8s/base/nginx-deployment.yaml` (+ `nginx-configmap.yaml`, `nginx-service.yaml`, `tls-secret.yaml`) — Deployment + LoadBalancer `Service` (80/443), the TLS-terminating entry point; config mirrors `nginx/gross-view.local.conf` for production domain `mint-box.ru`. `k8s/base/ingress.yaml` exists for reference but is NOT in the kustomize build (would conflict on node ports 80/443)
  - certbot → `k8s/base/certbot-cronjob.yaml` (+ `certbot-pvc.yaml`, `certbot-rbac.yaml`) — daily CronJob issuing/renewing the Let's Encrypt cert for `mint-box.ru` via HTTP-01 (webroot on the `certbot-data` PVC shared with nginx). On renewal it writes the `mint-box-tls` Secret and rolls the nginx Deployment
  - opencode → `k8s/base/opencode-deployment.yaml` (Deployment + `Service` + `opencode-data` PVC). Uses `ghcr.io/anomalyco/opencode` in web mode; file-based storage (no DB). **Manifests are currently commented out in `kustomization.yaml`** (planned phase 2, см. `docs/opencode-mcp-integration.md`) — in K8s the agent stays internal (ClusterIP, no LoadBalancer/hostPort). Both the docker-compose and k8s manifests use `OPENCODE_SERVER_USERNAME`/`OPENCODE_SERVER_PASSWORD` (Basic auth для Feign-клиента handler-а; в k8s — из Secret `gross-view-secrets`/`opencode_server_username`/`opencode_server_password`) plus `OPENCODE_MCP_URL`/`OPENCODE_MCP_TOKEN` to register the MCP server via `opencode/entrypoint.sh`. `BROWSER=none` disables the headless `xdg-open` error on startup. **Аналог docker-race-fix**: k8s не имеет `depends_on`/`condition`, поэтому `initContainer wait-for-keycloak` ждёт `/health/ready` на `http://keycloak.gross-view.svc.cluster.local:8080` (обязан совпадать с `gross-view-secrets/keycloak_internal_url`), прежде чем entrypoint попытается получить MCP-токен — иначе opencode стартует раньше готовности Keycloak и токен не выдается.
  - handler (gross-view backend, service name `gross-view-api`) → **no K8s manifests yet** — `k8s/base/nginx-configmap.yaml` already `proxy_pass`es `/api` to `gross-view-api.gross-view.svc.cluster.local:8082`, but deployments/services for it are still pending (phase 2 of `docs/opencode-mcp-integration.md`; image `gross-view.registry.twcstorage.ru/gross-view/gross-view-handler:latest` from the `../gross-view-handler` Dockerfile).
  - gross-view-ui → `k8s/base/gross-view-ui-deployment.yaml` (+ `gross-view-ui-service.yaml`) — **статическая SPA-посадочная страница gross-view-ui**. Deployment + internal ClusterIP `Service` (no LoadBalancer/hostPort). Image `gross-view.registry.twcstorage.ru/gross-view/gross-view-ui:latest` (реестр контейнеров Timeweb Cloud, «Артефактори» — хост `*.registry.twcstorage.ru`) собирается из `../gross-view-ui` (nginx:stable-alpine + уже собранный `dist/`, см. Dockerfile + `nginx/default.conf` — SPA fallback `try_files`). Pull из приватного реестра задан через `imagePullSecrets` → Secret `gross-view-registry` (`kubernetes.io/dockerconfigjson`, токен `registry-…` из панели Timeweb; создаётся командой `kubectl -n gross-view create secret docker-registry gross-view-registry --docker-server=gross-view.registry.twcstorage.ru --docker-username=gross-view --docker-password=<TOKEN>` или автоматически при подключении реестра к кластеру в панели — тогда имя секрета нужно поправить в манифесте). nginx `location /` проксирует на этот Service **порт 80** (`$gv_ui_upstream http://gross-view-ui.gross-view.svc.cluster.local:80`, раньше было 5173 = Vite dev-сервер). Probes: `GET /` на http-контейнерный порт 80. Публичный путь: `https://mint-box.ru` → main nginx (TLS) → `gross-view-ui` → статика. `k8s/base/ingress.yaml` (reference-only) в бэкенде `/*` тоже указывает на порт **80** — держать в синхроне с nginx-configmap.
- Secrets: `k8s/base/secret.yaml` holds placeholder values (`changeme`) in a single `gross-view-secrets` Secret. Fill real values before applying; for production use ExternalSecrets instead.
- Images: DockerHub is not directly reachable from the Moscow DC, so all Docker Hub images in the manifests are pulled via the Russian mirror `dockerhub.timeweb.cloud` (prefix `dockerhub.timeweb.cloud/`, e.g. `dockerhub.timeweb.cloud/library/nginx:stable-alpine`). Images from other registries stay as-is: `ghcr.io/anomalyco/opencode`, `quay.io/keycloak/keycloak`. **Собственные образы gross-view (gross-view-ui, будущий gross-view-handler) публикуются в реестре контейнеров Timeweb Cloud «Артефактори»** (`*.registry.twcstorage.ru`, напрямую доступен из Moscow DC — зеркалирование не нужно): `gross-view.registry.twcstorage.ru/gross-view/<service>:latest`, pull через `imagePullSecrets` → Secret `gross-view-registry`. GHCR-путь `ghcr.io/gross-view/*` больше не используется. When adding/updating a container image, keep the DockerHub→mirror prefix convention.
- TLS: in K8s the nginx pod terminates TLS using the `mint-box-tls` Secret. `k8s/base/tls-secret.yaml` creates a **bootstrap placeholder** `mint-box-tls` (self-signed cert for `mint-box.ru`) so the nginx pod can start before certbot has run. The certbot CronJob then overwrites this Secret with the real Let's Encrypt certificate (`kubectl create secret tls ... --dry-run=client -o yaml | kubectl apply -f -`) and rolls the nginx Deployment. Do not store real certs in the repo. The cert is issued for **`mint-box.ru` only** — `www.mint-box.ru` has no A record and is deliberately excluded from both the certbot `-d` list and the nginx `server_name` (see the LoadBalancer note below). Live cert issued 2026-09-06 (expires 2026-12-05); the certbot-cronjob deploy-hook writes the `mint-box-tls` Secret and patches nginx to roll it. The init container copies `kubectl` from `dockerhub.timeweb.cloud/lachlanevenson/k8s-kubectl:latest` — the version-pinned tag `:v1.28.4` does **not** exist on the mirror (ImagePullBackOff), use `:latest`.
- nginx upstream resolution: `k8s/base/nginx-configmap.yaml` resolves `keycloak`, `gross-view-api`, `gross-view-ui` **at request time** via `resolver kube-dns.kube-system.svc.cluster.local` + `set $..._upstream` variables in `proxy_pass`, so nginx starts even when those Services aren't deployed yet (a static `proxy_pass http://keycloak:8080` would abort startup with `[emerg] host not found in upstream`). This lets the stack be rolled out incrementally. Note: nginx does NOT resolve `<host>` in front of a `$variable` proxy_pass the same way — variable names must not contain `-`; use underscores. Readiness/liveness probes hit `GET /healthz` (served by nginx itself, 200), NOT `/` (which 301-redirects), so probes stay green before backends exist.
- Storage: `k8s/base/storageclass.yaml` declares `standard` (`rancher.io/local-path`, `WaitForFirstConsumer`) as default. The **cluster must run the Rancher local-path-provisioner** for PVCs to bind — k0s does NOT ship one by default, so on a fresh cluster install it first (e.g. `kubectl apply -f` the rancher/local-path-provisioner `deploy/local-path-storage.yaml`; keep the DockerHub→timeweb mirror convention for its images). Until it is installed, any `certbot-data`-like PVC stays `Pending` and dependent pods stay unscheduled.
- Cluster-specific changes (StorageClass, replicas) are applied by adding `patches` to the root `kustomization.yaml`. A nested `k8s/overlays` directory is NOT possible: kustomize forbids an overlay inside the repo root from including the root kustomization (cycle), and `configMapGenerator` cannot reach theme/realm files outside its own directory, so the root is the single build point.
- The cluster on Timeweb is **self-managed k0s** (single worker `worker-192.168.132.5`, k0s) with the Timeweb Cloud LoadBalancer controller (`k8s.timeweb.cloud/*` annotations) attached out-of-band (no controller pod in-cluster) — it provisions a **Timeweb balancer device** from each `LoadBalancer` Service. For a Service to get balancer rules, **every port needs `name` + `appProtocol` (e.g. `k8s.timeweb.cloud/proto-tcp`); without `appProtocol` the controller builds only one rule for the first port** (this was the cause of missing 443). `k8s/base/nginx-service.yaml` uses TCP passthrough (`proto-tcp`) on 80/443 so nginx keeps terminating TLS and serving ACME; the balancer does NOT terminate TLS. See https://timeweb.cloud/docs/k8s/network/kubernetes-load-balancer
- ⚠️ **Timeweb LoadBalancer health-check targets the node's port 80, NOT the NodePort.** Diagnosed 2026-09-06 via `tcpdump` on the node's `eth1`: the balancer (private IP `192.168.132.6`) probes the backend on `192.168.132.5:80` with a bare TCP connect (~every 30s) regardless of the `nginx` Service's `NodePort` (30571/30868). Nothing listened on host port 80 → SYN-ACK was answered with **RST** → backend marked "unavailable" → balancer dropped all traffic. **Fix:** `nginx-deployment.yaml` exposes the nginx container on `hostPort: 80`, so host port 80 is DNAT'd to the nginx pod whose `location /` returns 200. Keep `hostPort: 80` on the nginx container — removing it re-breaks the balancer health check. After this fix the balancer public IP `200.165.238.21` serves HTTP 200 on `/` and `/healthz`; `mint-box.ru` A-record points at the balancer's `EXTERNAL-IP` (`kubectl -n gross-view get svc nginx`), currently `200.165.238.21`. `www.mint-box.ru` has no A record (NXDOMAIN) and is intentionally not covered by the cert/nginx. certbot HTTP-01 validation succeeded 2026-09-06 — `https://mint-box.ru/healthz` returns 200 with a trusted Let's Encrypt chain, `https://mint-box.ru/sso` proxies to keycloak (301), `http://mint-box.ru/` returns 200 (meta-refresh redirect for the balancer health check).
- ⚠️ **Single-node `hostPort: 80` rollout deadlock.** Because nginx uses `hostPort: 80` and the cluster has one worker, `kubectl rollout restart deployment/nginx` or any nginx ReplicaSet change gets **stuck**: the new pod can't schedule (host port 80 still held by the old pod) and the old pod won't terminate until the new one is Ready — 0/1 Unschedulable, "didn't have free ports". Workaround when this happens: `kubectl -n gross-view scale deployment/nginx --replicas=0`, wait for pods to clear, then `--replicas=1`. The certbot deploy-hook (which `patch`es the Deployment) triggers this each renewal on a single node, so expect to run the scale 0→1 dance after each cert update.

## StatefulSet volumeClaimTemplates (immutable)

- `volumeClaimTemplates` in a StatefulSet is **immutable** after creation. Changing it
  (e.g. adding/removing `storageClassName`, size, accessModes) causes
  `Forbidden: updates to statefulset spec ... are forbidden` on `kubectl apply -k`.
- The postgres StatefulSet deliberately does NOT set `storageClassName` so the
  PVCs pick up the cluster's default StorageClass; do not re-add it. To force a
  specific StorageClass on a fresh cluster, recreate the StatefulSet with
  `kubectl delete statefulset <name> --cascade=orphan` (and its PVCs) first, or use
  a kustomize patch only on a cluster where the StatefulSet has never been created.

## Test cluster resource sizing

The test cluster runs on a single node: **1 CPU / 2 GB RAM / 30 GB NVMe**. All K8s manifests set CPU and memory **requests and limits** to fit within this budget. Total requests are ~525m CPU / ~1100Mi RAM, leaving headroom for system overhead (kubelet, OS, container runtime). When adding or modifying containers, verify the sum of all requests does not exceed ~800m CPU / ~1500Mi RAM to keep the scheduler happy. Note that **memory limits** determine OOM behavior, not scheduling: the keycloak pod's `1024Mi` limit is higher than typical node RAM share on purpose — a cold `start --import-realm` build on quay.io/keycloak/keycloak:23.0.6 peaks above 512Mi and gets OOMKilled (exit 137) at `512Mi`/`250m`, so keep the limits loose enough for the build even though the sum of limits may exceed physical RAM. CPU limits > request (500m vs 200m) can throttle during the build on a 1-CPU node — throttling does NOT kill, only slows startup.

| Service | CPU req/lim | Mem req/lim |
|---------|-------------|-------------|
| nginx | 50m / 100m | 32Mi / 64Mi |
| postgres | 150m / 200m | 448Mi / 512Mi |
| keycloak | 200m / 500m | 448Mi / 1024Mi |
| gross-view-ui | 50m / 100m | 32Mi / 64Mi |
| opencode | 75m / 150m | 128Mi / 256Mi |
