# AGENTS.md

## Project Overview

This repository manages **infrastructure configuration** for the "gross-view" project. It contains Keycloak realm settings, Nginx reverse proxy configuration, and custom CSS styles for authentication forms.

> **Requirement:** any change to the repo (files, services, network, code, config) — from an agent or a human — **must** be reflected back into this file (structure, notes, IP map, new services, new conventions). After every modification, review AGENTS.md and update it if the change makes current instructions inaccurate or incomplete.

## Purpose

This repo manages reverse proxy routing, Keycloak theme customizations, realm settings, and multi-container orchestration. Nginx provides unified entry point routing `/sso` to Keycloak, `/api` to the **handler backend (gross-view-handler)**, and `/` to frontend. The handler runs its own **MCP-сервер** (`/api/mcp`), к которому обязателен подключён ИИ-агент opencode (см. `docs/opencode-mcp-integration.md`).

## Infrastructure Services

### Static network

- Static network: every service has a fixed IP. In docker-compose **nginx публикует host-порты 80 и 443** (`0.0.0.0:80:80` / `0.0.0.0:443:443` — явная привязка ко всем интерфейсам хоста: nginx это единая точка входа сайта, без неё недоступны ни `https://gross-view.local`, ни канонический MCP-адрес `https://gross-view.local/api/mcp`; порты 80/443 на хосте должны быть свободны), keycloak (8080), postgres (5432, нужен хостовому handler-у в режиме отладки) и **opencode (4096)** тоже публикуют host-порты; внутри `keycloak_network` все сервисы доступны по статическим IP (`postgres` = `172.28.0.2`). **handler (gross-view-backend, порт 8082) в compose отсутствует** — он запускается в режиме отладки на хостовом компьютере, а nginx/opencode обращаются к нему через `host.docker.internal:8082`. **vault (8200) внутренний, без host-порта** — static IP `172.28.0.6`, доступен контейнерам сети `keycloak_network`; в K8s — ClusterIP `vault.gross-view.svc.cluster.local:8200` для будущего ESO. In K8s opencode stays internal (ClusterIP, no LoadBalancer/hostPort).
- **Автозапуск сервисов вместе с docker-демоном (2026-10-01):** в `docker-compose.yml` у **всех** сервисов выставлен `restart: always` (`postgres`, `nginx`, `keycloak`, `opencode`, `vault`), поэтому после загрузки хоста / `systemctl restart docker` стек поднимается сам, без ручного `docker compose up -d`. ⚠️ Политика рестарта фиксируется **при создании контейнера**: для уже существующих контейнеров после правки compose нужен `docker compose up -d` (пересоздаёт) либо разово `docker update --restart=always <container>`. У nginx `restart: always` спасает кейс «сертификата ещё нет»: контейнер падает с `cannot load certificate …` и сам поднимается, как только `scripts/generate-self-signed-cert.sh` создаст `.crt`/`.key` (но `up -d` всё равно нужно, чтобы контейнер вообще существовал). `always` (а не `unless-stopped`) выбран ради единообразия с остальным стеком: после ручного `docker compose stop` демон поднимет сервисы снова.
- `172.20.x`, `172.19.x`, `172.18.x` are taken by the host/WSL and other Docker networks — avoid them.

The realm's redirectUris contain both `gross-view.local` and `mint-box.ru` — keep these in sync when changing domains.

- **TLS-сертификат docker-compose (`gross-view.local`)** (2026-10-01): каталог `certs/` (в `.gitignore`) генерируется скриптом `scripts/generate-self-signed-cert.sh` (нужен `sudo chown "$(id -u):$(id -g)" certs`, только если каталог принадлежит root). Сертификат самоподписанный **с `CA:TRUE`**, поэтому `.crt` служит собственным trust anchor — отдельный CA-файл не нужен. Раздаётся **только монтированием каталога `./certs`**: nginx → `/etc/nginx/certs` (`ssl_certificate`/`ssl_certificate_key`, см. `nginx/gross-view.local.conf`), opencode → `/etc/ssl/gross-view/certs` (`NODE_EXTRA_CA_CERTS`), handler → `/etc/gross-view/certs` (импорт в JVM-cacerts). ⚠️ **Монтировать отдельный `.crt` файлом нельзя**: docker сам создаёт отсутствующий источник bind-mount как **каталог** (от root), после чего nginx падает с `cannot load certificate …: Is a directory` / `PEM_read_bio_X509_AUX … no start line`, а opencode — с нечитаемым `NODE_EXTRA_CA_CERTS`. Каталог `certs/` в репозитории обязателен (иначе compose пересоздаст его пустым), скрипт детектит «файл-каталог» и отказывается работать. **Файлы `.crt`/`.key` должны существовать ДО `docker-compose up`** — иначе получите `BIO_new_file … No such file or directory`. После перевыпуска: `sudo ./scripts/install-cert-system-trust.sh` (доверие на хосте: system CA store + NSS db для браузера, опционально `--jvm` для host-handler) + `docker-compose up -d nginx` + `docker-compose up -d opencode` (opencode нужно **пересоздать**, а не `restart` — CA-файл и монтирование фиксируются при создании контейнера) + повторный импорт в JVM-truststore handler'а. K8s этой локальной схемы не касается: там TLS терминирует nginx из Secret `mint-box-tls` (генерация в initContainer + certbot).
- **`/etc/hosts` на хосте должен содержать `127.0.0.1  gross-view.local`** (2026-10-01): nginx публикует 80/443 на хост, и без этой записи браузер/`curl` не находят `https://gross-view.local` (в т.ч. канонический MCP-адрес `https://gross-view.local/api/mcp`). Запись нужна **только хосту**; внутри сети контейнеров резолв отдельный — opencode получает `gross-view.local → 172.28.0.4` из `extra_hosts` (`docker-compose.yml`), nginx — встроенный DNS docker `127.0.0.11`. Домен пишется ровно как `gross-view.local`: он же в `server_name` и в SAN сертификата, опечатка («gross-viewe.local») даёт «неизвестный хост» + ошибку TLS. Правится вручную (`sudo`), в репозитории не хранится; в AGENTS.md/README зафиксировано как обязательный шаг «Быстрый старт».
- **nginx в docker-compose резолвит `keycloak` по DNS в момент запроса** (2026-10-01): `resolver 127.0.0.11 valid=10s ipv6=off;` + `set $keycloak_upstream keycloak:8080;` + `proxy_pass http://$keycloak_upstream;`. Статический `proxy_pass http://keycloak:8080` резолвится при загрузке конфига, и nginx падал с `host not found in upstream "keycloak"`, т.к. `depends_on` в compose даёт только порядок старта, а не готовность контейнера (имя резолвится, когда keycloak уже в сети). Побочный эффект: `/sso/` теперь срезается через `rewrite ^/sso/(.*)$ /$1 break;` — при переменной в `proxy_pass` nginx **не** подставляет префикс location автоматически, без rewrite запрос ушёл бы в keycloak как `/sso/...` и дал бы 404. `host.docker.internal` остался статическим: он приходит из `extra_hosts` (/etc/hosts) и резолвится всегда. Починка старта keycloak — отдельная задача (нет `condition: service_healthy`, keycloak поднимается ~60+ с).
- **Line endings:** `.gitattributes` pins `*.sh` to `text eol=lf` and `*.ps1` to `text eol=crlf` (overrides the local `core.autocrlf=true`). Never let shell scripts keep CRLF — a BusyBox ash container breaks with `/entrypoint.sh: set: line 2: illegal option -` (the `\r` becomes part of the `set` option). Create/edit scripts with LF only and keep `opencode/entrypoint.sh` ↔ `k8s/base/opencode-entrypoint-configmap.yaml` and `vault/entrypoint.sh` ↔ `k8s/base/vault-entrypoint-configmap.yaml` (embedded `data.entrypoint.sh` / `data.vault-config.hcl`) byte-identical; both opencode/vault pairs were regenerated to LF + clean UTF-8.
- MCP ↔ opencode (docker): **handler в docker-compose отсутствует** — backend `gross-view-handler` (Spring Boot, порт 8082) запускается локально в режиме отладки на хостовом компьютере, а nginx проксирует `/api` → `http://host.docker.internal:8082` (в opencode для этого прописан `extra_hosts: host.docker.internal:host-gateway`). Handler требует `CREDENTIAL_ENCRYPTION_KEY` (AES-GCM 32 байта, base64; fail-fast) Оба направления аутентифицируются **JWT реального пользователя**, отдельной учётки/токенов нет: handler → opencode (chat/analyze/providers/…) — pass-through текущего JWT (`Authorization: Bearer <jwt>`; opencode на внутренней сети, свои auth не имеет), opencode → `/api/mcp` — **пер-сессионный MCP-сервер, регистрируемый handler-ом** (с 2026-09-24 статичного OAuth больше нет): handler берёт токен из inbound-заголовка запроса (`Authorization: Bearer <JWT>`), при включённом Token Exchange (env `OPENCODE_MCP_TOKEN_EXCHANGE`) обменивает его на `aud=mcp` (RFC 8693, клиент `gross-view-handler-service`), и регистрирует на агенте изолированный сервер `gross-view-<workspaceId>-<userHash>-<sessionHash>` через `POST /mcp` с заголовками `Authorization: Bearer <mcp-jwt>` + `X-Workspace-Id`; при завершении сессии — `DELETE /mcp/{id}` (best-effort). OAuth-подключение (`opencode mcp auth gross-view`, публичный клиент `opencode-mcp`, redirect `http://127.0.0.1:19876/mcp/oauth/callback`) осталось только для **локального CLI** через свой `opencode.json`. Для контейнеризованного варианта `handler/entrypoint.sh` импортирует self-signed `gross-view.local.crt` в JVM-cacerts (`changeit`), поэтому для JWKS обязателен `extra_hosts: gross-view.local:172.28.0.4`. В realm добавлены роли `MCP`/`ANALYST`/`ADMIN`, **публичный** клиент `opencode-mcp` (CLI) и конфиденциальный `gross-view-handler-service` + клиент-ресурс `mcp` (audience Token Exchange); конфиденциальный клиент `opencode-agent` и service-account `service-account-opencode-agent` **удалены** из realm (2026-09-21). **LLM-ключи провайдеров приходят env-ом контейнера** (`DEEPSEEK_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY`, `GOOGLE_API_KEY`, `GROQ_API_KEY`, `MISTRAL_API_KEY`, `XAI_API_KEY`; проброс из `.env` через `docker-compose.yml`; k8s — `secretKeyRef` `gross-view-secrets/<provider>_api_key`) — сервер opencode читает их напрямую как credentials провайдеров. **Управление провайдерами моделей в рантайме** (`POST /opencode/providers/{id}/connect`, OAuth authorize/callback, `POST /opencode/models/sync`) работает через тот же пользовательский JWT и не требует новых Secret-ов; ключи провайдеров лежат в persistent volume opencode (см. `docs/opencode-mcp-integration.md`), флаг `OPENCODE_CATALOG_CREATE_MISSING` (default `false`) управляет созданием неизвестных моделей справочника при синхронизации. Детали/вопросы v1 vs v2 токенов — в `docs/opencode-mcp-integration.md`.

## Kubernetes (K8s) deployment

The `k8s/` directory mirrors the docker-compose stack for cloud/K8s. Both describe the same services; keep them in sync.

- Apply with `kubectl apply -k .` from the repo root. The **root** `kustomization.yaml` uses `configMapGenerator` to embed the Keycloak theme (`themes/gross-view/`) and realm (`gross-view-realm.json`) into ConfigMaps because kustomize cannot reference files outside its own directory.
- **`revisionHistoryLimit: 0`** is set on every Deployment (`nginx`, `keycloak`, `gross-view-ui`, `vault`, and the commented-out `opencode`) so old ReplicaSets for pods that no longer exist are cleaned up by the Deployment controller instead of accumulating (K8s default keeps 10). Keep this field on new Deployments. Note: it disables `kubectl rollout undo` rollback history — single-node nginx hostPort rollouts already rely on the scale 0→1 dance anyway.
- Service → manifest mapping (all in `gross-view` namespace):

- nginx upstream resolution: `k8s/base/nginx-configmap.yaml` resolves `keycloak`, `gross-view-api`, `gross-view-ui` **at request time** via `resolver kube-dns.kube-system.svc.cluster.local` + `set $..._upstream` variables in `proxy_pass`, so nginx starts even when those Services aren't deployed yet (a static `proxy_pass http://keycloak:8080` would abort startup with `[emerg] host not found in upstream`). This lets the stack be rolled out incrementally. Note: nginx does NOT resolve `<host>` in front of a `$variable` proxy_pass the same way — variable names must not contain `-`; use underscores. - Storage: `k8s/base/storageclass.yaml` declares `standard` (`rancher.io/local-path`, `WaitForFirstConsumer`) as default. The **cluster must run the Rancher local-path-provisioner** for PVCs to bind — k0s does NOT ship one by default, so on a fresh cluster install it first (e.g. `kubectl apply -f` the rancher/local-path-provisioner `deploy/local-path-storage.yaml`; keep the DockerHub→timeweb mirror convention for its images). - Cluster-specific changes (StorageClass, replicas) are applied by adding `patches` to the root `kustomization.yaml`. A nested `k8s/overlays` directory is NOT possible: kustomize forbids an overlay inside the repo root from including the root kustomization (cycle), and `configMapGenerator` cannot reach theme/realm files outside its own directory, so the root is the single build point.
- The cluster on Timeweb is **self-managed k0s** (single worker `worker-192.168.132.5`, k0s) with the Timeweb Cloud LoadBalancer controller (`k8s.timeweb.cloud/*` annotations) attached out-of-band (no controller pod in-cluster) — it provisions a **Timeweb balancer device** from each `LoadBalancer` Service. For a Service to get balancer rules, **every port needs `name` + `appProtocol` (e.g. `k8s.timeweb.cloud/proto-tcp`); without `appProtocol` the controller builds only one rule for the first port** (this was the cause of missing 443). `k8s/base/nginx-service.yaml` uses TCP passthrough (`proto-tcp`) on 80/443 so nginx keeps terminating TLS and serving ACME; the balancer does NOT terminate TLS. See https://timeweb.cloud/docs/k8s/network/kubernetes-load-balancer
- ⚠️ **Timeweb LoadBalancer health-check targets the node's port 80, NOT the NodePort.** Diagnosed 2026-09-06 via `tcpdump` on the node's `eth1`: the balancer (private IP `192.168.132.6`) probes the backend on `192.168.132.5:80` with a bare TCP connect (~every 30s) regardless of the `nginx` Service's `NodePort` (30571/30868). Nothing listened on host port 80 → SYN-ACK was answered with **RST** → backend marked "unavailable" → balancer dropped all traffic. **Fix:** `nginx-deployment.yaml` exposes the nginx container on `hostPort: 80`, so host port 80 is DNAT'd to the nginx pod whose `location /` returns 200. Keep `hostPort: 80` on the nginx container — removing it re-breaks the balancer health check. After this fix the balancer public IP `200.165.238.21` serves HTTP 200 on `/` and `/healthz`; `mint-box.ru` A-record points at the balancer's `EXTERNAL-IP` (`kubectl -n gross-view get svc nginx`), currently `200.165.238.21`. `www.mint-box.ru` has no A record (NXDOMAIN) and is intentionally not covered by the cert/nginx. certbot HTTP-01 validation succeeded 2026-09-06 — `https://mint-box.ru/healthz` returns 200 with a trusted Let's Encrypt chain, `https://mint-box.ru/sso` proxies to keycloak (301), `http://mint-box.ru/` returns 200 (meta-refresh redirect for the balancer health check).
- ⚠️ **Single-node `hostPort: 80` rollout deadlock.** Because nginx uses `hostPort: 80` and the cluster has one worker, `kubectl rollout restart deployment/nginx` or any nginx ReplicaSet change gets **stuck**: the new pod can't schedule (host port 80 still held by the old pod) and the old pod won't terminate until the new one is Ready — 0/1 Unschedulable, "didn't have free ports". Workaround when this happens: `kubectl -n gross-view scale deployment/nginx --replicas=0`, wait for pods to clear, then `--replicas=1`. The certbot deploy-hook (which `patch`es the Deployment) triggers this each renewal on a single node, so expect to run the scale 0→1 dance after each cert update.

## StatefulSet volumeClaimTemplates (immutable)

- `volumeClaimTemplates` in a StatefulSet is **immutable** after creation. Changing it
  (e.g. adding/removing `storageClassName`, size, accessModes) causes
  `Forbidden: updates to statefulset spec ... are forbidden` on `kubectl apply -k`.
- The postgres StatefulSet deliberately does NOT set `storageClassName` so the
  PVCs pick up the cluster's default StorageClass; do not re-add it. To force a
  specific StorageClass on a fresh cluster, recreate the StatefulSet with
  `kubectl delete statefulset <name> --cascade=orphan` (and its PVCs) first, or use
  a kustomize patch only on a cluster where the StatefulSet has never been created.

## Test cluster resource sizing

The test cluster runs on a single node: **1 CPU / 2 GB RAM / 30 GB NVMe**. All K8s manifests set CPU and memory **requests and limits** to fit within this budget. Total requests are ~710m CPU / ~1328Mi RAM (including opencode + vault + vpn-gateway with its nginx proxy; opencode manifests are commented out), leaving headroom for system overhead (kubelet, OS, container runtime). When adding or modifying containers, verify the sum of all requests does not exceed ~800m CPU / ~1500Mi RAM to keep the scheduler happy. Btw, the nginx TLS-bootstrap initContainers transiently add `+20m CPU / +24Mi RAM` requests while a pod starts (they exit after bootstrap). Note that **memory limits** determine OOM behavior, not scheduling: the keycloak pod's `1024Mi` limit is higher than typical node RAM share on purpose — a cold `start --import-realm` build on quay.io/keycloak/keycloak:23.0.6 peaks above 512Mi and gets OOMKilled (exit 137) at `512Mi`/`250m`, so keep the limits loose enough for the build even though the sum of limits may exceed physical RAM. CPU limits > request (500m vs 200m) can throttle during the build on a 1-CPU node — throttling does NOT kill, only slows startup.

| keycloak | 200m / 500m | 448Mi / 1024Mi |
